Red Team / Application Security Assessment Report

Project Title: SecureShop Security Assessment Laboratory Date: October 1, 2026
Methodology: Build → Attack → Identify → Fix → Retest Scope: Local Environment Only (http://127.0.0.1:8080)
Assessment Tool: OWASP ZAP (Zed Attack Proxy) Language & Stack: Python, Flask, SQLite, HTML5, CSS3, JavaScript

1. Executive Summary

This laboratory assessment report documents the end-to-end security audit, penetration testing, and defense-in-depth remediation of SecureShop, an e-commerce web application. The target was evaluated against four core vulnerability categories from the OWASP Top 10:2021 framework and evaluated for outdated dependencies.

The assessment proved that insecure baseline development patterns allowed unauthorized privilege escalation, database exfiltration, and session manipulation. Subsequent engineering fixes—including input parameterization, strict server-side role enforcement, cryptographic hashing, and modern security headers—successfully neutralized all findings, confirmed via automated unit tests and DAST verification.

2. System Architecture

The application implements a modular three-tier architecture running locally on port 8080:

Client Browser <=== HTTP Requests / Cookies ===> Flask Application <=== SQLite Queries ===> database.db

Primary Modules:

  • Public Services: Catalogue browsing, real-time item search, and product specifications.
  • Authentication: User registration, login verification, and session lifecycle.
  • Customer Services: Shopping cart, multi-item checkout, personal profile, and order receipts.
  • Administrative Portal: Privilege-restricted inventory manager, system dashboard, and user accounts directory.

3. Vulnerability Findings & Investigation

Finding 1: Broken Function Level Authorization & IDOR

OWASP Category: A01:2021 – Broken Access Control
High Severity
Affected URL & Functionality
http://127.0.0.1:8080/admin/dashboard, /admin/products, /admin/users, /order/<id>
WHAT? (Vulnerability Description)
In vulnerable mode, the server only verifies that an active session exists ('user_id' in session), failing to verify administrative role privileges. Standard customer accounts can access administrative controls and view/modify other users' profiles and private invoices.
WHERE? (Code Location)
routes/admin.py (in enforce_admin_check()) and routes/user.py (in profile() and order_detail()).
WHY? (Root Cause)
Missing server-side role validation and lack of authorization ownership checks prior to rendering privileged views.
IMPACT
Privilege escalation from normal customer to site administrator, unauthorized deletion of inventory, and confidentiality breach of customer addresses.
EVIDENCE
Logging in as standard user alice and navigating directly to /admin/dashboard successfully returns HTTP 200 OK and renders the admin console. Navigating to /order/102 renders customer Bob's private home delivery address.
REMEDIATION
Enforce role verification if session.get("role") != "admin": abort(403) on all admin endpoints, and verify record ownership on user resources.
RETEST
In secure mode, access attempts by non-admin users consistently return HTTP 403 Forbidden.

Finding 2: Unsanitized SQL Query Construction (SQL Injection)

OWASP Category: A03:2021 – Injection
High Severity
Affected URL & Functionality
http://127.0.0.1:8080/search?q=<payload> (Product Catalogue Search)
WHAT? (Vulnerability Description)
The search functionality interpolates raw user input into an SQL query string via string formatting without parameter binding, permitting arbitrary SQLite command execution.
WHERE? (Code Location)
routes/public.py in the search() function.
WHY? (Root Cause)
Dynamic SQL query assembly using Python f-strings instead of prepared statements.
IMPACT
Extraction of the complete SQLite database contents (including account credentials, order history, and private user details) via UNION-based attacks.
EVIDENCE
Submitting ' OR '1'='1 returns all store products. Submitting ' UNION SELECT id, username, email, password, role, bio, created_at FROM users-- dumps all user records into the search results page.
REMEDIATION
Implemented parameterized SQL queries using SQLite positional placeholders (?): 
cursor.execute("SELECT * FROM products WHERE name LIKE ? OR description LIKE ?", (f"%{query}%", f"%{query}%"))
RETEST
Submitting injection payloads in secure mode safely returns zero results without syntax errors; input is treated strictly as literal strings.

Finding 3: Debug Mode Active & Missing HTTP Defensive Headers

OWASP Category: A05:2021 – Security Misconfiguration
Medium Severity
Affected URL & Functionality
http://127.0.0.1:8080/debug/error and all HTTP response headers.
WHAT? (Vulnerability Description)
Flask's interactive Werkzeug debugger was enabled (debug=True), exposing source code, local filesystem paths, and environment frames upon unhandled errors. Defensive HTTP headers (X-Frame-Options, X-Content-Type-Options, Content-Security-Policy) were missing.
WHERE? (Code Location)
config.py (VulnerableConfig.DEBUG = True) and app.py (apply_security_headers()).
WHY? (Root Cause)
Development convenience flags left active in runtime environments.
IMPACT
Information disclosure aiding attacker reconnaissance; vulnerability to Clickjacking and MIME-type confusion attacks.
EVIDENCE
Navigating to /debug/error exposes the full interactive Werkzeug traceback. Response headers lack X-Frame-Options and expose Server: Werkzeug/2.2.2 Python/3.14.
REMEDIATION
Disabled debug mode (DEBUG = False), added generic error handlers (403, 404, 500), and enforced strict HTTP response headers (X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Content-Security-Policy).
RETEST
Errors return a clean generic page without stack traces; headers verified via curl and DevTools.

Finding 4: Plaintext Password Storage & Insecure Session Attributes

OWASP Category: A07:2021 – Identification and Authentication Failures
Medium Severity
Affected URL & Functionality
http://127.0.0.1:8080/register, /login, and session cookie lifecycle.
WHAT? (Vulnerability Description)
Passphrases were saved in the SQLite database in raw cleartext. The session key was a static hardcoded string. Session cookies omitted HttpOnly and SameSite attributes, and sessions were not cleared on login (Session Fixation).
WHERE? (Code Location)
config.py and routes/auth.py.
WHY? (Root Cause)
Omission of modern password hashing libraries and secure cookie flag directives.
IMPACT
Instant credential compromise if the database is read; exposure of session cookies to client-side JavaScript theft via XSS.
EVIDENCE
Direct database inspection shows plain password strings. Executing console.log(document.cookie) in browser DevTools successfully displays the session identifier.
REMEDIATION
Implemented salted one-way password hashing (scrypt / PBKDF2), dynamic 256-bit secret keys (secrets.token_hex(32)), SESSION_COOKIE_HTTPONLY = True, SESSION_COOKIE_SAMESITE = 'Lax', and session.clear() on authentication.
RETEST
New registrations store hashes beginning with scrypt:; session cookies cannot be read via JavaScript.

4. Outdated Component Analysis (A06:2021)

Component Name Werkzeug (WSGI web utility library underpinning Flask)
Baseline Version Used 2.2.2 (Intentionally pinned in baseline)
Current Patched Version 3.1.9
Security Advisory / CVE CVE-2023-30861 (CVSS v3.1: 7.5 High)
Risk Description In Werkzeug < 2.2.3, responses that set cookies without explicit caching headers omit the Vary: Cookie HTTP header. Downstream shared caches (CDNs, reverse proxies) cache the Set-Cookie header and deliver it to subsequent users, resulting in unauthorized account takeover.
Remediation Path Upgraded requirement specification to Werkzeug >= 3.1.9.

7. Conclusion

The SecureShop project demonstrates the vital importance of defensive secure coding practices.
